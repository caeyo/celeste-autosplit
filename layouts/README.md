# layouts

The memory layouts the auto splitter reads, as Rust, one file per game flavour.
[`memory.rs`](../autosplitter/src/memory.rs) includes each file as a module,
which rustfmt leaves as it is. A file can hold constants that `memory.rs`
doesn't read: Everest's version bytes, say, or a path added to the manifest
before its reader. What gets measured is listed in the layout probe's
[`Manifest.cs`](../tools/layout-probe/Manifest.cs), described in its
[README](../tools/layout-probe/README.md#the-manifest).

| File | What | Made by |
|---|---|---|
| `windows-xna.rs`, `windows-fna.rs`, `linux.rs`, `macos.rs` | Each vanilla flavour's measured layout. | The [layout probe](../tools/layout-probe/), through the Layouts workflow. Don't edit them by hand. |
| `everest.rs` | Everest's own info struct. | Transcribed from Everest's source. |

## Regenerating

Run the Layouts workflow, from the Actions tab or with:

```sh
gh workflow run layouts.yml --ref <branch>
```

It runs the probe on every vanilla flavour, then opens a pull request into
`<branch>` with the regenerated files, from the branch `layouts/<branch>`. If
nothing changed, it says so and opens nothing. A later run updates an open pull
request instead of opening another. The run uses `<branch>`'s workflow and
probe, so changes can be tried before they're merged. The pull request's own
workflow runs wait until someone approves them, since the workflow opens it
with `GITHUB_TOKEN`.

For each flavour, the probe runs inside the game's own runtime, next to the real
game files. It:

1. resolves every name in the manifest, and measures each path's offsets;
2. checks that the flavour's hand-written signature matches the root's anchor
   method once, in its compiled code, and that the earliest store pattern match
   after it holds the slot's address, within the window the auto splitter
   searches;
3. constructs the game for real (`new Celeste()`), in a process named like the
   game. Then it writes distinctive values into every number and flag, and into
   strings that are still null, and reads every path back raw from the slot, as
   the auto splitter does.

Then the probe writes the flavour's layout and holds the game. The layout
replaces the committed one, the auto splitter is rebuilt with it, and the
[live check](../harness/) attaches the auto splitter to the probe's process: it
must report the values the probe holds.

Any failure fails the run, and no pull request is opened. The workflow also runs
on pull requests from this repository that change the auto splitter, the
layouts, the harness or the probe. There, each committed layout must be the one
the probe writes: a difference is a hand edit, or a change to the manifest
without regenerating. To run the probe yourself, see its
[README](../tools/layout-probe/README.md).

## `<flavour>.rs`

Abbreviated from `windows-fna.rs`:

```rust
// Generated by the layout probe, through the Layouts workflow: don't edit it by hand. See
// layouts/README.md.
//
// Flavour: windows-fna
// Celeste.exe: version 1.4.0.0, module version ID d7b2abb4-05ec-4c97-9545-49f0a02e4a41

/// As `asr::get_os` names it.
pub const OS: &str = "windows";
pub const POINTER_SIZE: u64 = 4;
/// Where a string holds its length, an `i32`.
pub const STRING_LENGTH: u64 = 0x4;
/// Where a string's UTF-16 characters start.
pub const STRING_CHARS: u64 = 0x8;

/// `Celeste.Celeste::Instance`: its slot is found from the compiled code of its anchor,
/// `Celeste.Celeste::.ctor()`.
pub mod celeste_instance {
    /// Matches the code once: hex bytes, with `??` for any byte.
    pub const SIGNATURE: &str = "68 38 04 00 00 68 c0 03 00 00 68 1c 02 00 00 ff 35";
    /// The store into the slot: the earliest match of any of these after the signature, with `SS`
    /// for the slot's address.
    pub const STORES: &[&str] = &[
        "8d 15 SS SS SS SS e8",
    ];
    /// How many bytes after the signature are searched for the store, which ends within them.
    pub const STORE_WINDOW: u64 = 256;

    // Each path's offsets from the object in the slot, and the name and type of each field
    // along it.

    /// Title: System.String
    pub const TITLE: [u64; 1] = [0x84];
    /// AutoSplitterInfo: Celeste.AutoSplitterInfo, Chapter: System.Int32
    pub const AUTO_SPLITTER_INFO_CHAPTER: [u64; 2] = [0xa0, 0x18];
}
```

| Part | Meaning |
|---|---|
| The header | The flavour, and the probed `Celeste.exe`: the game's version, as the game sets it (the assembly's own version is 1.0.0.0), and its module version ID. The three FNA flavours share one `Celeste.exe`. |
| `OS` | `windows`, `linux` or `macos`, as `asr::get_os()` names them. |
| `POINTER_SIZE` | 4 or 8 bytes. |
| `STRING_LENGTH`, `STRING_CHARS` | Where a string object holds its length (an `i32`) and its UTF-16 characters. |
| A module per root | Named after the root's type and field: `Celeste.Celeste::Instance` is `celeste_instance`. |
| &emsp;`SIGNATURE` | The manifest's hand-written signature, which matches the anchor's code once: hex bytes, `??` for any byte. |
| &emsp;`STORES` | The manifest's hand-written store patterns: the code that stores into the slot, after the signature. The earliest match of any of them after the signature holds the slot's address, in its 4 or 8 `SS` bytes. Earliest, because a 4-byte pattern can also match inside an 8-byte store. |
| &emsp;`STORE_WINDOW` | How many bytes after each signature match the auto splitter searches for the store: `StoreWindow` in the manifest. |
| &emsp;An array per path | Each field's offset, one per hop, named after the manifest's path: `AutoSplitterInfo.Chapter` is `AUTO_SPLITTER_INFO_CHAPTER`. Its comment gives each field's name and .NET type. The path's length is part of its type, so `memory.rs` checks that each field's pointer path has room for it when it compiles. |

All offsets are in bytes, from the address a reference to the object holds. To read
a path, read the root's object from the slot. Then each offset but the last leads to
a pointer to the next object, and the last one to the value.

The anchor's machine code isn't stored: it embeds addresses that change on every
run. The probe prints it in the run's log.

## `everest.rs`

Everest publishes its own struct, `CoreAutoSplitterInfo`, at the start of a memory
mapping of its own. The auto splitter finds it by checking the start of each memory
region for the struct's magic bytes. The file is transcribed by hand from the
source linked at its top: each field's offset, as a constant named after the
field, with its type in a comment, then each flag's bit. To update it,
transcribe the struct again at a newer commit, and update the link.
