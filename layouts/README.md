# layouts

The memory layouts the auto splitter reads, as Rust, one file per runtime the game runs on.
[`memory.rs`](../autosplitter/src/memory.rs) includes each file as a module,
which rustfmt leaves as it is. A file can hold constants that `memory.rs`
doesn't read: Everest's version bytes, say, or a path added to the manifest
before its reader. What gets measured is listed in the probe's
[`Manifest.cs`](../tools/probe/Manifest.cs), described in its
[README](../tools/probe/README.md#the-manifest).

| File | What | Made by |
|---|---|---|
| `clr32.rs`, `mono64.rs` | The measured layout of the game on each runtime: 32-bit .NET Framework for Windows's XNA and FNA builds, and 64-bit Mono for Linux's and macOS's. | The [probe](../tools/probe/), through the Layouts workflow. Don't edit them by hand. |
| `everest.rs` | Everest's own info struct. | Transcribed from Everest's source. |

## Regenerating

Run the Layouts workflow, from the Actions tab or with:

```sh
gh workflow run layouts.yml --ref <branch>
```

It runs the probe on every vanilla flavour, then opens a pull request into
`<branch>` with the regenerated files, from the branch `layouts/<branch>`. If
nothing changed, it says so and opens nothing. A later run updates an open pull
request instead of opening another. The run uses `<branch>`'s workflow and
probe, so changes can be tried before they're merged. The pull request's own
workflow runs wait until someone approves them, since the workflow opens it
with `GITHUB_TOKEN`.

Every flavour on a runtime has to measure the same file, since the game's own
classes lay out the same on them, apart from what `memory.rs` reads from the
game's code. A pull request's layout check holds each of them to it. On dispatch,
one flavour's file replaces another's, and the pull request it opens runs that
check.

Each probe job only regenerates its own runtime's file, but `memory.rs` builds
with both. So `memory.rs` can only use what both committed layouts already
hold: add a new path to the manifest and regenerate, and only then write its
reader. A change to what the probe writes that `memory.rs` depends on, such as
the files' format, has to convert the committed files in the same change.

For each flavour, the probe runs inside the game's own runtime, next to the real
game files. It:

1. resolves every name in the manifest, and measures each path's offsets;
2. checks that the runtime's hand-written signature matches the root's anchor
   method once, in its compiled code, and that the earliest store pattern match
   after it holds the slot's address, and the last match of the field store's
   pattern before it holds the field's measured offset, each within the window
   the auto splitter searches;
3. constructs the game for real (`new Celeste()`), in a process named like the
   game.

Then the probe writes the runtime's layout, which replaces the committed one, and
the auto splitter is rebuilt with it. The [harness](../harness/) starts the probe
again, and runs the live check and the replay against it: see its README.

Any failure fails the run, and no pull request is opened. The workflow also runs
on pull requests that change the auto splitter, the layouts, the harness, the
probe or the traces, from forks once a maintainer approves the run. There, each
committed layout must be the one the probe writes: a difference is a hand edit,
or a change to the probe (its manifest or its output) without regenerating. To
run the probe yourself, see its [README](../tools/probe/README.md).

## `<runtime>.rs`

Abbreviated from `clr32.rs`:

```rust
// Generated by the probe, through the Layouts workflow: don't edit it by hand. See
// layouts/README.md.
//
// Celeste.exe: version 1.4.0.0

/// In bytes.
pub const POINTER_SIZE: u64 = 4;
/// Where a string holds its length, an `i32`.
pub const STRING_LENGTH: u64 = 0x4;
/// Where a string's UTF-16 characters start.
pub const STRING_CHARS: u64 = 0x8;

/// `Celeste.Celeste::Instance`: its slot is found from the compiled code of its anchor,
/// `Celeste.Celeste::.ctor()`.
pub mod celeste_instance {
    /// Matches the code once: hex bytes, with `??` for any byte.
    pub const SIGNATURE: &str = "68 38 04 00 00 68 c0 03 00 00 68 1c 02 00 00 ff 35";
    /// The store into the slot: the earliest match of any of these after the signature, with `SS`
    /// for the slot's address.
    pub const STORES: &[&str] = &[
        "8d 15 SS SS SS SS e8",
    ];
    /// How many bytes after the signature are searched for the store, which ends within them.
    pub const STORE_WINDOW: u64 = 256;
    /// The store of `AutoSplitterInfo`: the last match of this before the signature, with `SS` for
    /// the field's offset, which depends on the framework the game runs on.
    pub const AUTO_SPLITTER_INFO_STORE: &str = "8d 96 SS SS SS SS e8";
    /// How many bytes before the signature are searched for it, which starts within them.
    pub const AUTO_SPLITTER_INFO_STORE_WINDOW: u64 = 128;

    // Each path's offset after `AutoSplitterInfo`, and the name and type of each field
    // along it.

    /// AutoSplitterInfo: Celeste.AutoSplitterInfo, Chapter: System.Int32
    pub const AUTO_SPLITTER_INFO_CHAPTER: u64 = 0x18;
}
```

The comments say what each constant is. Beyond them:

- The header's version is the game's, as the game sets it: the assembly's own
  version is 1.0.0.0.
- Each root gets a module named after its type and field
  (`Celeste.Celeste::Instance` is `celeste_instance`), and each path a constant
  named after the path (`AutoSplitterInfo.Chapter` is
  `AUTO_SPLITTER_INFO_CHAPTER`), with its offset after `AutoSplitterInfo`.
- `SIGNATURE` and `STORES` are the manifest's hand-written patterns, and
  `STORE_WINDOW` is its `StoreWindow`. The store is the earliest match of any
  store pattern, because a 4-byte pattern can also match inside an 8-byte
  store.
- `AUTO_SPLITTER_INFO_STORE` and its window are the manifest's too, for its
  `CodeField`. `memory.rs` reads `AutoSplitterInfo`'s offset from that store, so
  the layout doesn't hold it. The field comes after those of the framework's
  `Game` class, and Everest replaces the FNA that vanilla runs on, so its offset
  depends on the Everest version.

All offsets are in bytes, from the address a reference to the object holds. To read
a path, read the root's object from the slot, and from it, at the offset read from
the code, `AutoSplitterInfo`'s object. The path's offset leads from there to the
value.

The anchor's machine code isn't stored: it embeds addresses that change on every
run. The probe prints it in the run's log.

## `everest.rs`

Everest's own struct, `CoreAutoSplitterInfo`, transcribed by hand: the file's
header says where it comes from, what it holds, and how to update it. The auto
splitter finds the struct by checking the start of each memory region for its
magic bytes.
